# Урок 13. Безопасность, мониторинг и эксплуатация

**Цель:** измерить производительность кластера, наблюдать за его здоровьем по ключевым метрикам и понимать, как защищают Kafka в промышленной эксплуатации.

### Теория

**Безопасность** строится из трёх слоёв ([Security](https://kafka.apache.org/43/security/security-overview/)):

| Слой | Что решает | Основные средства |
| --- | --- | --- |
| Шифрование | Трафик нельзя прочитать по сети | TLS (шифрование соединения, как в https; протоколы `SSL`, `SASL_SSL`) |
| Аутентификация | Кто подключается | TLS-сертификаты (электронные «удостоверения» участников), SASL (набор способов проверки логина и пароля: PLAIN, SCRAM, GSSAPI, OAUTHBEARER) |
| Авторизация | Что разрешено делать | ACL (списки прав: кто что может делать с каким топиком), утилита `kafka-acls.sh`, `StandardAuthorizer` |

В наших уроках использовался открытый протокол `PLAINTEXT` (передача без шифрования): он годится только для локального обучения.

**Мониторинг.** Брокеры публикуют метрики (числовые показатели работы) через JMX (стандартный механизм Java для выдачи таких показателей). Самые полезные для начала:

| Метрика (JMX) | Что показывает | Норма |
| --- | --- | --- |
| `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` | Партиции, у которых не хватает синхронных реплик | 0 |
| `kafka.controller:type=KafkaController,name=OfflinePartitionsCount` | Партиции без лидера | 0 |
| `kafka.controller:type=KafkaController,name=ActiveControllerCount` | Является ли узел активным контроллером | ровно один узел кластера возвращает 1 |
| `kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec` | Скорость входящих сообщений | зависит от нагрузки |
| `kafka.network:type=RequestMetrics,name=TotalTimeMs,request=Produce` | Время обработки запросов на запись | стабильно, без резких скачков |

Метрики клиентов не менее важны: лаг консьюмеров (урок 5), задержка и ошибки продюсеров.

**Эксплуатация.** Что нужно уметь: корректно останавливать брокер и обновлять кластер по одному узлу, следить за свободным местом на диске, находить недореплицированные партиции (у которых отстала часть копий), возвращать лидерство на предпочтительные реплики.

### Практика

**Шаг 1. Измерьте пропускную способность**

```bash
bin/kafka-topics.sh --create --topic perf --partitions 3 --bootstrap-server localhost:9092

bin/kafka-producer-perf-test.sh --topic perf --num-records 200000 --record-size 200 \
  --throughput -1 --bootstrap-server localhost:9092
```

Утилита печатает число записей в секунду, среднюю и максимальную задержку. Запишите результат. Затем повторите тест, добавив `--command-property acks=all`, и сравните: насколько изменились скорость и задержка?

Чтение:

```bash
bin/kafka-consumer-perf-test.sh --topic perf --bootstrap-server localhost:9092 --num-records 200000
```

**Шаг 2. Посмотрите метрики через JMX**

Остановите брокер и запустите его с открытым JMX-портом (JDK включает программу `jconsole`):

```bash
JMX_PORT=9999 bin/kafka-server-start.sh config/server.properties
# в другом терминале
jconsole localhost:9999
```

В закладке MBeans найдите метрики из таблицы выше. Запустите `kafka-producer-perf-test.sh` и наблюдайте рост `MessagesInPerSec`.

**Шаг 3. Найдите проблему в кластере** (кластер из урока 6)

1. Остановите узел 2.
2. Выполните:

```bash
bin/kafka-topics.sh --describe --under-replicated-partitions --bootstrap-server localhost:9092
```

1. Запишите, у каких партиций пропали реплики. Запустите узел 2 и повторите команду: список должен опустеть.

**Шаг 4. Восстановите распределение лидеров**

После возврата узла лидеры могут остаться неравномерно распределёнными. Запросите перевыбор предпочтительных лидеров:

```bash
bin/kafka-leader-election.sh --bootstrap-server localhost:9092 \
  --election-type PREFERRED --all-topic-partitions
bin/kafka-topics.sh --describe --topic resilient --bootstrap-server localhost:9092
```

Если всё уже сбалансировано, команда сообщит, что выбирать некого; это нормально.

**Шаг 5. Права доступа (разбор без запуска)**

Чтобы включить ACL, на брокере задают класс авторизатора и суперпользователей, а клиентов подключают по защищённому протоколу. Пример команды выдачи прав пользователю на чтение топика группой (для справки, на нашем открытом стенде она не сработает):

```bash
bin/kafka-acls.sh --bootstrap-server localhost:9092 --add \
  --allow-principal User:alice --operation Read --operation Describe \
  --topic orders --group shop-service
```

Прочитайте разделы [Authorization and ACLs](https://kafka.apache.org/43/security/authorization-and-acls/) и [Listener Configuration](https://kafka.apache.org/43/security/listener-configuration/) и письменно ответьте: какие три настройки брокера нужны, чтобы включить TLS и авторизацию, и какие операции нужны консьюмеру группы на топик и на группу?

### Что дальше

В Kafka 4.2 функция «очереди для Kafka» (share groups, [KIP-932](https://kafka.apache.org/42/getting-started/upgrade/)) объявлена готовой к промышленному использованию: она позволяет нескольким консьюмерам обрабатывать одну партицию как очередь с индивидуальным подтверждением событий. Для знакомства с ней изучите раздел Consumer and Share Consumer Configs и утилиту `kafka-console-share-consumer.sh`.
