# Урок 9. Гарантии доставки

**Цель:** выбирать настройки продюсера и консьюмера под нужную семантику доставки и проверить их поведение при отказах.

### Теория

Ответ на вопрос «не потеряется ли событие и не придёт ли оно дважды» зависит от трёх звеньев: подтверждений записи (`acks`), повторов продюсера и момента коммита у консьюмера.

**Подтверждения продюсера (`acks`)**

| Значение | Когда запись считается успешной | Риск |
| --- | --- | --- |
| `0` | Не ждём подтверждения | Событие может потеряться незаметно |
| `1` | Подтвердил лидер партиции | Потеря, если лидер упал до репликации |
| `all` | Подтвердили все реплики из ISR (не меньше `min.insync.replicas`) | Выше задержка; при нехватке реплик запись отклоняется |

**Идемпотентный продюсер** (идемпотентность — свойство операции: повторное выполнение не меняет результат; параметр `enable.idempotence=true`) защищает от дублей при повторной отправке: Kafka узнаёт событие по номеру и отбрасывает копию. Он требует `acks=all`. В Java-клиенте режим включён по умолчанию; в `confluent-kafka` (librdkafka) его лучше включать явно.

**Транзакции** позволяют записать несколько событий в разные топики и партиции атомарно (всё сразу или ничего): либо видны все, либо ни одно. Продюсер получает `transactional.id`, а консьюмер, чтобы не видеть незавершённые и отменённые записи, ставит `isolation.level=read_committed`.

**Семантики доставки**

| Семантика | Как достигается | Что возможно |
| --- | --- | --- |
| Не более одного раза (at-most-once) | Коммит offset до обработки | Потери |
| Не менее одного раза (at-least-once) | Коммит offset после обработки, `acks=all` | Повторы |
| Ровно один раз (exactly-once) | Идемпотентность и транзакции; в Kafka Streams включается настройкой | Без потерь и повторов внутри Kafka |

Замечание: «ровно один раз» относится к цепочке «читаем из Kafka, обрабатываем, пишем в Kafka». Если обработка меняет внешний мир (отправляет письмо, пишет в чужую базу), нужна дополнительная защита, например идемпотентная запись по уникальному идентификатору.

### Практика

Понадобится кластер из трёх брокеров из урока 6 (все узлы запущены).

**Шаг 1. Топик со строгим требованием к репликам**

```bash
bin/kafka-topics.sh --create --topic strict --partitions 1 --replication-factor 3 \
  --config min.insync.replicas=3 \
  --bootstrap-server localhost:9092,localhost:9192,localhost:9292
```

Запись с `acks=all` теперь успешна только при трёх живых репликах.

**Шаг 2. Нормальная работа**

```bash
bin/kafka-console-producer.sh --topic strict --command-property acks=all \
  --bootstrap-server localhost:9092,localhost:9192,localhost:9292
> событие при полном составе
```

**Шаг 3. Отказ одного узла**

Остановите узел 3. Кворум контроллеров сохранится (живы два из трёх), но реплик в ISR станет две, меньше требуемых трёх. Повторите запись с короткими тайм-аутами (предельным временем ожидания ответа):

```bash
bin/kafka-console-producer.sh --topic strict --command-property acks=all \
  --command-property request.timeout.ms=3000 --command-property delivery.timeout.ms=6000 \
  --bootstrap-server localhost:9092,localhost:9192
> событие при неполном составе
```

Ожидается ошибка о нехватке синхронных реплик (`NOT_ENOUGH_REPLICAS`) или истечении тайм-аута доставки. Теперь выполните то же с `--command-property acks=1`: запись пройдёт, но её надёжность ниже. Запишите вывод обоих вариантов и сделайте вывод о цене `acks=all`. Верните узел 3 в строй.

## Урок 9 (продолжение). Идемпотентность и транзакции на Node.js

Шаги 1–3 урока 9 приведены выше (они работают на консольных утилитах). Шаги 4 и 5 для JavaScript выглядят так.

**Шаг 4. Идемпотентный продюсер.** Идемпотентность (повтор отправки не создаёт дубликатов: брокер узнаёт повтор по номеру продюсера и порядковому номеру сообщения) включается одной настройкой. В `producer.js` из урока 7 замените создание продюсера:

```javascript
const producer = new Kafka().producer({
  'bootstrap.servers': BOOTSTRAP,
  'enable.idempotence': true,
});
```

Запустите скрипт как раньше. Изменение не видно в выводе, поэтому задание на понимание: изучите в документации клиента параметры `acks`, `retries`, `max.in.flight.requests.per.connection` и `delivery.timeout.ms` и объясните, как они связаны с идемпотентностью и какие значения клиент выставляет сам при её включении.

**Шаг 5. Транзакции.** Транзакция записывает группу сообщений так, что читатель увидит либо все, либо ни одного. Создайте топик `tx-demo` (одна партиция, на кластере из Docker Compose — три реплики) и файл `tx.js`:

```javascript
const { Kafka } = require('@confluentinc/kafka-javascript').KafkaJS;

const BOOTSTRAP = process.env.BOOTSTRAP || 'localhost:9092';
const mode = process.argv[2]; // commit или abort

async function main() {
  const producer = new Kafka().producer({
    'bootstrap.servers': BOOTSTRAP,
    'transactional.id': 'demo-tx',
  });
  await producer.connect();

  const tx = await producer.transaction();
  for (let i = 0; i < 3; i++) {
    await tx.send({ topic: 'tx-demo', messages: [{ key: 'k', value: `${mode}-${i}` }] });
  }
  if (mode === 'commit') {
    await tx.commit();
  } else {
    await tx.abort();
  }
  await producer.disconnect();
}

main().catch((err) => {
  console.error('Ошибка:', err);
  process.exit(1);
});
```

Запустите `node tx.js commit`, затем `node tx.js abort`. Прочитайте топик консольным консьюмером дважды (команда ниже):

```bash
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic tx-demo \
  --from-beginning --timeout-ms 5000 --isolation-level read_committed
```

С `read_committed` должны быть видны только `commit-0`, `commit-1`, `commit-2`; повторите команду с `--isolation-level read_uncommitted` и сравните: отменённые сообщения тоже попадут в вывод, потому что они записаны в журнал, но помечены как отменённые.

Что важно знать: `transactional.id` должен быть стабильным и уникальным для продюсера (при перезапуске с тем же значением брокер «закрывает» незавершённую транзакцию предыдущего экземпляра); транзакция гарантирует атомарность записи, а не обработку на стороне читателя.

Статус проверки: `tx.js` запускался только на имитации кластера из библиотеки клиента; поведение `read_committed` на настоящем брокере не проверялось, поэтому сверяйте результат с описанием выше.
